# v0.6.0: spec-first agents and Resource Principal

Release date: 2026-10-06.

## Highlights

### Spec-first agent creation

`oci-agent-new` now starts every new agent from a specification, never from
code.

1. **Describe the agent** in a few sentences, in your language.
2. **The skill drafts `agent-spec.md`**, starting from the **business
   context**: the customer persona (internal customers included), the use
   case, the expected outcomes, and, optionally, the customer's concerns such
   as security or scalability. If the request does not give the persona, the
   use case, or the outcomes, the skill asks for them first.
3. **Proven defaults are written into the draft**, marked "(default)":
   regions, runtime variables, HTTP status codes, handling of ambiguous
   requests, deterministic functional checks, packaged data. They come from
   the skill's agent guidelines, which collect what real releases taught.
4. **You review and edit the specification**, by hand or in the chat. Nothing
   else is generated until you approve it.
5. **After approval, the skill generates the agent code and the manifest**,
   following the specification and the guidelines' code-quality rules
   (structured LLM output, timeouts, logging, startup checks), ready to build
   and deploy.

The specification stays in the agent repository: it is the shared reference
for the developer, the customer, and the next iteration.

### Resource Principal for agents that call OCI Generative AI

An agent can now call OCI Generative AI **with no API key**: the Hosted
Application authenticates as itself through Resource Principal.

* Select it with `GENAI_AUTH_MODE=resource_principal` and a Generative AI
  project (`GENAI_PROJECT_ID`). API-key mode remains the default.
* The agent code uses the `oci-genai-auth` library; the guidelines include a
  single `make_client` function for both modes.
* [IAM policies](../iam-policies.md) lists the runtime policies for Resource
  Principal and for API keys.

### Simpler and safer API keys

* Agent secrets such as `GENAI_API_KEY` can live in the tool's `.env`: one
  place for every agent and every client (Codex CLI, VS Code extension,
  Claude Code), without exporting anything.
* Every runtime report shows `from_env` values as `value=<hidden>`, with
  their origin (environment or tool `.env`).

### Setup check

`scripts/check_setup.sh` (PowerShell: `check_setup.ps1`) runs the existing
read-only checks in one command: tenancy file, Docker build environment, OCI
CLI and region, installed skills, and, with `--manifest`, the agent manifest
and its OCIR repository. Each check reports `PASS` or `FAIL`.

## Upgrading from v0.5.0

1. `git pull` in the tool checkout. The installed skills are links, so they
   update at once; start a new Codex session.
2. Optional: move `GENAI_API_KEY` from each agent folder into the tool's
   `.env`, using the commented example in `.env.example`; then never share or
   commit that file.
3. Optional: run `scripts/check_setup.sh`.

Existing agents and Hosted Applications need no change.
