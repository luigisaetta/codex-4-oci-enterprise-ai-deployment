# v0.7.0: asynchronous agents, protected agents, safer operation

Release date: 2026-10-13.

## Highlights

### Asynchronous agents

Agents that run several steps, for example several LLM calls, can now take
minutes per request
([Spec 024](../../specs/024-asynchronous-agents.md)).

* **A standard contract.** `POST /<path>` checks the input at once and
  answers 202 with a job reference; `GET /<path>/{job_id}` reports the status
  of each step and, at the end, the result or a business error message.
* **`oci-agent-new` generates it.** When the request describes several steps
  or a long job, the skill drafts the specification with a Steps section,
  describes the behavior in plain words, and generates the code and a
  manifest with one replica.
* **Functional checks follow the job.** A check with `poll` starts the job
  and reads its status until it ends; `local: false` keeps a check out of the
  local verification when it can run only in OCI.
* **The demo UI shows the progress.** The page starts the job, shows each
  step with its business label as it completes, then the result.

### Number of replicas

An optional `deploy.scaling` section sets the minimum and maximum number of
replicas when the Hosted Application is created (1 to 30)
([Spec 023](../../specs/023-replica-scaling-at-creation.md)). Asynchronous
agents use one replica, so that every status request reaches the replica that
holds the job.

### Agents protected with JWT tokens, end to end

The `public-idcs` profile is now verified live
([Spec 010](../../specs/010-jwt-inbound-authentication.md)).

* **A step-by-step guide** for the identity-domain confidential application:
  [Protecting an agent with JWT tokens](../idcs-confidential-application.md),
  with an editable script that tests a token and shows its claims, never the
  token.
* **The verifier reads the client ID and secret from the tool's `.env`**: no
  export before starting Codex.
* **The demo UI works with protected agents**: its local server requests the
  token; the browser never sees it
  ([Spec 022](../../specs/022-idcs-credentials-for-ui-and-verifier.md)).

### Safer operation

* **Missing runtime permissions stop the release with a clear message**
  (exit 27): when the Hosted Deployment cannot read its image, the deploy
  says what the tenancy administrator must add, and Codex never changes IAM
  itself ([Spec 019](../../specs/019-stop-on-missing-runtime-permissions.md)).
* **The customer name approved for demos** (`Supremo`, or
  `DEMO_CUSTOMER_NAME`) is the only one written to files and shown in demos;
  the real customer's name stays in the conversation
  ([Spec 020](../../specs/020-demo-customer-name.md)).
* **Rules that always apply live in `AGENTS.md`**, which Codex reads in every
  session, with or without a skill: each agent repository receives the
  customer-name and IAM rules (`scripts/agent_instructions.py ensure`), and
  sessions that only use the skills never edit the tool's own files
  ([Spec 021](../../specs/021-protect-the-tool-home.md)).

### Easier setup

* Getting started in two complete guides,
  [macOS and Linux](../getting-started-macos-linux.md) and
  [Windows](../getting-started-windows.md) (PowerShell 7, Docker Desktop or
  Podman), with the audience stated and venv or pyenv as alternatives to
  Conda.
* [Logging in to OCIR](../ocir-login.md): the registry username from the
  Console's Profile menu, the auth token, and common errors.
* The tenancy administrator's steps, including what a new compartment needs,
  in [Setup for the administrator](../iam-policies.md#setup-for-the-administrator).
  Vulnerability-scanning policies are not needed: the runtime needs only
  `read repos`.

### Native Windows

A Windows pilot fixed the PowerShell deploy (the networking JSON passed as
one argument, which had broken every first application creation), added a
readable summary of OCI CLI errors, and Conda hooks so that the OCI CLI works
under PowerShell 7.

## Upgrading from v0.6.0

1. `git pull` in the tool home. The installed skills are links, so they
   update at once; start a new Codex session.
2. For each existing agent folder, add the rules to its `AGENTS.md` once,
   from the tool home:

   ```bash
   python scripts/agent_instructions.py ensure --target <agent-folder>
   ```

3. For agents with `public-idcs`: put `OCI_AGENT_IDCS_CLIENT_ID` and
   `OCI_AGENT_IDCS_CLIENT_SECRET` in the tool's `.env` (see `.env.example`).
4. Demo UIs created before this release keep the old server bridge; to use
   them with a `public-idcs` or asynchronous agent, create the UI again with
   `oci-agent-ui`.
5. Optional: set `DEMO_CUSTOMER_NAME` in the tool's `.env` if your approved
   demo name is not `Supremo`.

Existing agents and Hosted Applications need no change.
